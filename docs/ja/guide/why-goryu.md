# なぜ Goryu なのか

Goryu は、シンプルな手書きの REST API から AI/LLM サービスまで、バックエンドを構築するためのバッテリー同梱型の Go フレームワークです。人間にとって生産的であり、LLM が生成しやすいように設計されています。ストリーミングファーストで、可観測性が高く、デフォルトで安全です。

2 つのことが同時に真であり、Goryu はその両方に応えます。人間は今なお自らコードを書くため、素の REST API は Rails/Phoenix のような使い心地で、手作業でも極めて簡単に構築できなければなりません。そして Go は、ゲートウェイ、エージェントサーバー、推論プロキシといった AI/LLM バックエンドを構築する場でもあります。そのため Goryu は、それらが必要とするプリミティブをバッテリーとして同梱しています。

## 課題

Go のエコシステムには優れたルーターが数多くありますが、Rails/Phoenix スタイルの、本番運用まで一気通貫で導いてくれるバッテリー同梱型フレームワークは存在しません。ルーター、バリデーション、エラーハンドリング、ロギング、ヘルスチェック、メトリクス、グレースフルシャットダウンを、すべて自分で組み立てる必要があります。

AI/LLM バックエンドの構築はさらに大変です。今日それは、同じインフラを何度も手作業で作り直すことを意味します。

- **SSE / ストリーミング** によるトークンレスポンス。フラッシュとバックプレッシャーを正しく配線する必要があります。
- リクエストごとの **トークンとコストの計測**。キー単位・トークン単位の予算管理を伴います。
- **プロンプトをキーとしたレスポンスキャッシュ** — URL ではなく `POST` のボディをキャッシュします。
- 上流の LLM API に対する **プロバイダプロキシ**。クライアントへストリーミングで中継します。
- オフライン評価のためにリクエスト/レスポンスのペアを取り込む **評価記録（eval recording）**。

これらはどれも目新しいものではありませんが、どのチームも繰り返し作り直し、そしてエッジケースを取りこぼしてしまいます。

## Goryu が提供するもの

`goryu.New()` を呼ぶだけで、ヘルスチェック、メトリクス、構造化ロギング、グレースフルシャットダウンがそのまま手に入ります。セットアップは不要です。ハンドラは単なる関数であり、バリデーション付きの型付き入力はわずか 1 回の呼び出し（`goryu.Bind[T]`）で実現できます。

必要になったとき、そしてそのときだけ、AI プリミティブが用意されています。

- **ファーストクラスのストリーミング**: `c.SSE(...)` と `c.Stream(...)`。加えて型付きストリーミング JSON（`goryu.StreamJSON[T]`、`goryu.SSEJSON[T]`）と WebSocket ヘルパー（`websocket.Upgrade`）。
- **[トークン & コスト計測](/ja/middleware/aimeter)**: `middleware/aimeter` — キー単位/トークン単位のレート制限と USD 建てのコスト計上。
- **[プロンプトキャッシュ](/ja/middleware/promptcache)**: `middleware/promptcache` — LLM エンドポイント向けのボディをキーとしたレスポンスキャッシュ。加えてストリーミング対応のリバースプロキシヘルパー（`aiproxy`）。
- **[評価記録](/ja/middleware/recorder)**: `middleware/recorder` — 評価データセット用にリクエスト/レスポンスのペアを NDJSON として取り込みます。
- **LLM フレンドリーな DX**: `llms.txt` と機械可読な API リファレンス（`App.MountLLMs`）、MCP サーバー（`goryu mcp`）、そして AI スキャフォールド（`goryu scaffold ai <name> --kind=chat|rag|agent`）。

これらはすべて追加的なものです。手書きの REST アプリが、使わない AI 機能のコストを払うことは決してありません。

## Goryu との比較

Goryu は「単なるもう 1 つの高速ルーター」ではありません。その領域は Gin、Fiber、Echo、Chi が押さえています。Goryu の強みは、素の REST サービスと AI バックエンドの **両方** において本当に優れていて、しかもシンプルなケースを複雑にしない点にあります。

| | Goryu | Gin | Fiber | Echo | Chi |
|---|---|---|---|---|---|
| 高速ルーター | あり | あり | あり | あり | あり |
| バッテリー同梱（ヘルス、メトリクス、ロギング、グレースフルシャットダウン） | あり | なし | 一部 | 一部 | なし |
| CLI + スキャフォールディング | あり | なし | なし | なし | なし |
| ストリーミングファースト（SSE、型付きストリーミング、WebSocket） | あり | 手動 | 手動 | 手動 | 手動 |
| 組み込みのトークン/コスト計測 | あり | なし | なし | なし | なし |
| プロンプトをキーとしたキャッシュ + プロバイダプロキシ | あり | なし | なし | なし | なし |
| 評価記録 | あり | なし | なし | なし | なし |
| デフォルトで安全（すべてのレスポンスパスで） | あり | なし | なし | なし | なし |
| LLM フレンドリー（`llms.txt`、MCP サーバー） | あり | なし | なし | なし | なし |

率直にまとめると、素の REST API については、Goryu は Gin と同等の速さでありながら、はるかに多くの機能を組み込みで備えています。AI バックエンドについては、本来なら手作業で作り込むはずのパーツがすでにバッテリーとして用意されており、しかもシンプルなケースはシンプルなまま保たれます。

## 設計原則

1. **シンプルなケースはシンプルなまま** — 手書きの REST API が、使わない AI 機能のコストを払うことは決してあってはなりません。
2. **まず人間のために作り、次に LLM にとってフレンドリーに** — 同じクリーンな API が両者に応えます。
3. **デフォルトで安全に、すべてのレスポンスパスで。**
4. **ストリーミングは後付けではなく、ファーストクラスの市民です。**
5. **コアは小さく安定に保ち、広がりは contrib に持たせる。**
6. **LLM が正しい Goryu のコードを確実に生成できないなら、その API は凝りすぎです。**
